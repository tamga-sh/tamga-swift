# Machine-file fixtures — provenance

Every `.machine` file in this directory was produced by the **tamga-api server's own
`encode_machine_file`** (`src/shared/crypto/machine_file.rs`), driven through the same
`check_out_machine` payload shape the live checkout endpoint builds. None of them was
generated by this repository, and none of them may be regenerated here.

## Why that rule exists

`MachineFile`'s reading of the wire format was wrong in three separate ways for roughly two
years, in this SDK and in the other seven, and CI was green the whole time. The reason is
that every repo tested its verifier against a certificate it had encoded itself, with a
helper that made the same three mistakes as the verifier. The two halves agreed with each
other and neither agreed with the server, so the suite could not observe the bug it was
supposed to prevent — and no SDK could open a file the server actually issued.

A fixture this repo produced can only ever confirm this repo's assumptions. A fixture the
server produced is the only kind that can contradict them.

If a case is needed that this set does not cover, ask for it to be generated from the
server's encoder. Do not hand-write one, and do not synthesise one with `CheckoutFixture`.
`CheckoutFixture`'s machine helpers exist for negative/structural cases only, and they are
themselves cross-checked against these files by
`MachineFileServerFixtureTests.encFramingMatchesTheManifest`.

## What the set covers

12 files: 4 signing schemes × 3 variants.

| scheme | `alg` (plain / encrypted) |
|---|---|
| `Ed25519Sign` | `base64+ed25519+v2` / `aes-256-gcm+ed25519+v2` |
| `EcdsaP256Sign` | `base64+ecdsa-p256+v2` / `aes-256-gcm+ecdsa-p256+v2` |
| `Rsa2048Pkcs1Sign` | `base64+rsa-sha256+v2` / `aes-256-gcm+rsa-sha256+v2` |
| `Rsa2048Pkcs1PssSign` | `base64+rsa-pss-sha256+v2` / `aes-256-gcm+rsa-pss-sha256+v2` |

Variants per scheme: `plain_valid`, `encrypted_valid`, `plain_expired`.

`manifest.json` carries, per fixture: `file`, `alg`, `encrypted`, `enc_is_dot_separated`,
`public_key_b64`, `kid`, `license_key`, `fingerprint`, `expired`, `scheme`.

## Public key encodings

`public_key_b64` is the account public key exactly as the server's API publishes it
(`accounts/serializer.rs`, populated by `crypto/key_material.rs`) — **not** normalised into
one encoding for the SDK's convenience:

| scheme | encoding | length |
|---|---|---|
| Ed25519 | raw public key | 32 bytes |
| ECDSA P-256 | uncompressed X9.63 point (`0x04 ‖ X ‖ Y`) | 65 bytes |
| RSA-2048 | PKCS#1 `RSAPublicKey` DER | 270 bytes |

The ECDSA one is a real finding, not a fixture quirk: this SDK used to require X.509
`SubjectPublicKeyInfo` and so could not verify any genuine ECDSA machine file. See
`Crypto/Ecdsa.swift`.

## Expiry

The valid fixtures carry a one-hour TTL relative to their own `iat`, so they are already
expired by wall-clock time. Tests must verify at a clock derived from the file's signed
`iat` (`MachineFileServerFixtureTests.claims(of:)`), never at `Date()` — a suite pinned to
the wall clock passes on the day the fixtures were generated and fails every day after.

## Refreshing

Fixtures are regenerated from the server, not from here. When a new set lands, copy the
whole directory including `manifest.json`; the tests iterate the manifest, so extra
fixtures are picked up with no code change. Regenerating one file without its manifest
entry will fail as a key mismatch that looks exactly like a signature bug.
